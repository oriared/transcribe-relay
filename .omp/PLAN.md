Transcribe Relay передаёт аудио и видео с клиентской машины на сервер с Buzz и сохраняет расшифровку рядом с исходником. Серверная и клиентская части реализованы; текущий этап — проверка отказоустойчивости и приёмка на поддерживаемых платформах.
- `.omp/AGENTS.md` задаёт архитектуру, `.omp/RULES.md` — правила разработки: простой код, тесты обычных и граничных случаев, Ruff, отдельное согласование изменений API и разрешение на commit/push.
На Linux проверен Buzz 1.4.5 (Snap) с `QT_QPA_PLATFORM=offscreen`: для WAV создан TXT, а для повреждённого файла процесс вернул 0 без TXT. Поэтому адаптер проверяет результат, не обращаясь к внутренней БД Buzz. При развёртывании под другой учётной записью отдельно проверить доступ Buzz к каталогу заданий и модели.
## Утверждённая архитектура
- Сервер: Python 3.12+, `fastapi`, `uvicorn`; без `uvicorn[standard]`, multipart и ORM. Клиент: Python 3.9+, стандартная библиотека и только для Python 3.9–3.10 — `tomli`. Тесты — `unittest`; Ruff — инструмент разработки. Buzz установлен отдельно.
- TOML-конфиги через `tomllib` (на Python 3.9–3.10 — `tomli`), стандартный `logging`; секреты не писать в журнал. Сервер запускается одним экземпляром без `--reload` и нескольких Uvicorn workers; дополнительно захватывает `fcntl.flock` на файле в каталоге состояния. Клиент аналогично блокирует собственный state-каталог.
## Требования к реализованному поведению
В `src/transcribe_relay/` сервер разделён на `server.py` (HTTP и запуск), `config.py` (настройки), `storage.py` (SQLite и файлы), `worker.py` (очередь) и `buzz.py` (CLI). На клиенте `client.py` ведёт цикл обработки, `client_state.py` отслеживает файлы и хранит журнал, `client_http.py` передаёт файлы и публикует TXT. Допустимые расширения общие для обеих частей (`media.py`).
**Утверждённый HTTP API:**
Операции изменения параметров Buzz, отмены и управления историей в контракт не входят. Изменения HTTP API требуют отдельного согласования.
Клиентская SQLite (`client_state.py`) находится в отдельном `state_dir`, вне наблюдаемого каталога. Журнал хранит абсолютный путь, размер, `mtime_ns`, ключ загрузки, SHA-256 после подготовки, серверный UUID, стадию обработки и путь результата. Клиент сначала фиксирует операцию локально, затем посылает HTTP; повтор той же загрузки использует прежний ключ.
## Результаты проверки на 24 ноября 2026
- На Linux с Python 3.12.3 прошли 47 тестов, `ruff check` и `ruff format --check`. Для повторения из корня проекта после установки `python -m pip install '.[server,dev]'`: `python -m unittest discover -s tests -v`, `ruff check src tests`, `ruff format --check src tests`.
- Автотесты проверяют идемпотентность, разграничение доступа, оборванные загрузки, восстановление очереди, последовательный запуск и таймаут Buzz, обнаружение стабильных файлов, конфликт TXT и повтор только `/ack` после сохранения. В CI клиентские тесты также выполняются без серверных зависимостей.
- В сквозном прогоне на Linux с настоящим Buzz исходный файл, лежавший до запуска клиента, был пропущен. Новый WAV дал одно задание и локальный TXT; после `acknowledged` исходник остался, каталог задания на сервере удалён. **Доставка проверена, точность распознавания — отдельно:** для `Front_Center.wav` модель `tiny` в этом прогоне вернула `front Santa`, а не ожидаемую фразу. На macOS сквозной прогон не выполнялся.
- Целевое окружение — доверенная сеть/VPN. Клиент при первой инициализации пропускает уже существующие файлы, чтобы не отправить архив записей без намерения оператора.
- На целевой установке проверить экспорт TXT под пользователем службы. Проверка Linux/Snap 1.4.5 не гарантирует работу других сборок Buzz. Если CLI не завершает обработку без ручного вмешательства или не экспортирует TXT, не считать установку готовой к эксплуатации.
## Дальнейшие шаги

1. **Восстановление после потери ответа на загрузку.** Добавить регрессионный сценарий: сервер принял POST, ответ потерян, исходник заменён либо удалён до повтора. Сейчас журнал может перевести старую операцию в `obsolete` до сохранения серверного UUID. Сравнить хранение неизменяемой локальной копии до получения UUID (дополнительный диск) с поиском задания по ключу (изменение API, сначала согласовать). Критерий: клиент находит прежнее задание, получает его TXT без второй транскрибации и не считает новую версию файла обработанной вместо старой.
2. **Остановка сервера при аварии worker.** Воспроизвести исключение SQLite в `Store.claim()` или `Store.finish()`: сейчас `server.py` ожидает задачу worker только при остановке. Обеспечить наблюдаемую ошибку и завершение службы, чтобы supervisor мог её перезапустить. Проверка: API не продолжает принимать задания без worker; после рестарта очередь сохраняется, прерванное `running` становится `failed`.
3. **Приёмка клиента на macOS.** Добавить клиентские тесты на macOS в `.github/workflows/ci.yml` без серверных extras. Проверить с Linux-сервером обрыв связи после сохранения TXT, перезапуск клиента и восстановление сети: повторяется только `/ack`, локальный файл не переписывается, сервер завершает очистку.
4. **Проверка ожидаемой фразы.** На целевой установке под пользователем службы прогнать через клиент и сервер разборчивый WAV с заранее записанной эталонной фразой. Зафиксировать образец, версию Buzz, модель и язык. Сравнить локальный TXT с фразой без учёта регистра и пунктуации; успешная доставка сама по себе эту проверку не закрывает.
5. **Версионирование правил проекта.** Согласовать включение `.omp/PLAN.md`, `.omp/RULES.md` и полной рабочей версии `.omp/AGENTS.md` в Git. После согласования проверить, что свежий клон содержит те же правила и критерии приёмки, что и рабочая копия.
