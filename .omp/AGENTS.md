## Архитектура
- Сервер — Python 3.12+, FastAPI/Uvicorn. Клиент macOS/Linux — Python 3.9+, без GUI; на Python 3.9–3.10 для TOML требуется `tomli`.
- Один серверный процесс: HTTP API и один последовательный worker. Без Redis, Celery и ORM.
- Серверная SQLite хранит состояния и FIFO-очередь; исходники и TXT — на диске, в отдельных каталогах заданий.
- Buzz установлен отдельно, запускается через CLI без shell, по одному процессу. Успех — завершившийся процесс с кодом 0 и корректный UTF-8 TXT; одного появления файла недостаточно. Работу установленного Buzz без GUI проверить отдельно.
- Клиент хранит состояние в локальной SQLite, сканирует один каталог без рекурсии и симлинков каждые 2 секунды. При первой инициализации существующие файлы пропускает; затем обрабатывает новые и изменённые, в том числе за время остановки. Перед загрузкой ждёт 10 секунд стабильности размера и mtime.
- Конфигурация — TOML, журналирование — logging. Минимум зависимостей, приоритет простоты сопровождения.
## HTTP и жизненный цикл
- Отдельный Bearer-токен каждого клиента; доступны только его задания. HTTP допустим внутри доверенной сети/VPN, вне неё нужен HTTPS.
- `POST /v1/jobs?filename=...` — поток исходника, `Content-Length`, `Idempotency-Key`, `X-Content-SHA256`; возвращает ID после полного сохранения. Повтор с тем же ключом и метаданными возвращает прежнее задание.
- `GET /v1/jobs/{id}` — состояние; `GET /v1/jobs/{id}/result` — TXT; `POST /v1/jobs/{id}/ack` — подтверждение сохранения клиентом.
- Статусы: `queued → running → completed → acknowledged`; ошибка обработки — `failed`. После рестарта прежние `running` становятся `failed`, без автоматического повторного запуска Buzz.
- Загрузки потоковые, с проверкой размера, SHA-256 и настроенного лимита. Неполные загрузки в очередь не попадают.
- Клиент опрашивает задания каждые 5 секунд. Сетевые повторы сохраняют ключ загрузки и состояние операции.
- Результат сохраняется атомарно рядом с исходником как `<полное имя исходника>.txt`, без перезаписи отличающегося файла. Только после надёжного сохранения клиент отправляет ack.
- Ack идемпотентен: сервер удаляет файлы задания, но сохраняет запись-квитанцию. Неподтверждённые результаты автоматически не удаляются; исходники клиента не удаляются.
